# 磁盘占用估算

> 本文估算 weread-shelf 的本地 SQLite 数据库在长期运行下需要多少磁盘空间。
> 落库方式见 [data-flow.md](data-flow.md)，表结构见 [`app/models.py`](../app/models.py)。
> 数据基于一次**只读实测**（2026-06-29，单个真实账号），仅供量级参考。

## 结论先行

- **量级很小**：首次全量同步后约 **3–5MB**；之后默认每天同步一次，**约 5KB/天 ≈ 2MB/年**。
  跑十年也就二三十 MB，SQLite 单文件完全够用。
- **绝大部分表有上界**：`book`、`chapter`、`bookmark`、`review`、`period_stat` 采用 upsert/覆盖写入，
  体积由书库和阅读量决定，不随时间无限增长。
- **唯一随时间线性增长的是 `pull_run`**（每次同步一行，约 150B/行，每年约 50KB），可忽略。
- **封面图不进库**：书架封面是浏览器直连微信读书 CDN 拉的，不占数据库。

## 一、两类表

落库分两种写法（见 [data-flow.md](data-flow.md) §三），磁盘增长特性完全不同：

| 类别 | 表 | 增长驱动 | 是否随时间无限增长 |
|---|---|---|---|
| **upsert（就地覆盖）** | `book` `chapter` `bookmark` `review` `period_stat` `shelf_item` `recommendation` | 书库规模、阅读/划线量 | 否，有上界 |
| **追加日志** | `pull_run` | 同步次数 | **是**，但每天仅一行，可忽略 |

> `shelf_item` 和 `recommendation` 现已改为 upsert 模式（`book_id` 单独主键），每次 pull 覆盖
> 而非追加。历史快照不再保留，体积恒定。

## 二、初始量（首次全量同步后）

upsert 类表大小由书库和阅读量决定，不随时间涨。以下行数取自实测账号（书架 71 本、
有笔记 82 本、划线 2285 条、想法+书评 674 条）：

| 表 | 行数 | 单行估算 | 小计 |
|---|---|---|---|
| `book` | ~100 本（书架 ∪ 笔记 ∪ 推荐去重） | ~0.9KB（`intro` 是大头） | ~90KB |
| `chapter` | ~100 本 × 平均 ~80 章 ≈ 8000 行 | ~100B | ~0.8MB |
| `bookmark` | 2285 行 | ~260B（含 `mark_text` 正文） | ~0.6MB |
| `review` | 674 行 | ~1–1.5KB（`content` 最长，抽样均 800+ 字） | ~0.8–1MB |
| `period_stat` | 回填历史周期 ~400 行 | ~500B | ~200KB |
| `shelf_item` | 71 行（当前书架） | ~60B | ~4KB |
| `recommendation` | 12 行（当前推荐） | ~500B | ~6KB |

> 合计约 2.7MB 数据，加索引与 SQLite 页开销后 **≈ 3–5MB**。
> 空库（仅建表）本身约 100KB，是占用下限。

## 三、日常增长量

稳态下每次 pull 只追加一行 `pull_run`（~150B），其余表全部原地覆盖：

| 表 | 每次 pull 行为 | 日均增长 |
|---|---|---|
| `shelf_item` | upsert 当前书架，淘汰已下架的书 | ~0KB（大小恒定） |
| `recommendation` | 全量替换为最新 12 本 | ~0KB（大小恒定） |
| `book` / `chapter` / `bookmark` / `review` | upsert 覆盖 | 仅渐进的阅读增量 |
| `period_stat` | 覆盖当前/上一周期 | ~0KB |
| `pull_run` | 追加一行 | ~150B |
| **合计** | | **< 5KB/天**（含渐进的书/笔记增量） |

叠加持续阅读新增的划线/想法、以及推荐/书架轮换带入 `book` 表的新书：

| 周期 | 估算 |
|---|---|
| 每天 | ~2–5KB |
| 每年 | **~1–2MB** |
| 5 年 | ~5–10MB |
| 10 年 | ~10–25MB |

> 同步频率从「每天」改成「每 6 小时」**不会**让磁盘翻倍：除 `pull_run`（每次一行、~150B）
> 外所有表都是覆盖写入，一天内多次同步不产生额外行。

## 四、如需控制体积

长期运行的体积几乎全部来自 `bookmark` / `review` / `chapter` 等有界表——它们由你的阅读量
决定，且都是你想要保留的笔记和目录数据。

唯一无限增长的是 `pull_run`（同步执行日志），按每天一行算，十年约 50KB，无需操心。

**如果确实想清理 pull_run 历史**：

admin 页的「数据保留」设置可限制 pull_run 保留天数（默认不限制）。设为 N 天后，
每次同步成功后自动删除早于 N 天的旧记录，始终保留最新一条和最近一条成功的。

**手动一次性回收**（例如想立刻缩小文件）：

```sql
DELETE FROM pull_run WHERE started_at < '2025-01-01';
VACUUM;   -- 回收已删页，真正缩小文件
```
