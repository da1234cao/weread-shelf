# 拉取与存储逻辑(从页面操作角度)

本文从"在页面上做了什么操作 → 背后发生了哪些拉取/存储"的角度,说明 weread-shelf
的数据流。配套文档:接口契约见 [api.md](api.md),需求见 [requirements.md](requirements.md)。

## 心智模型

> 整个网站 = **一个本地 SQLite 文件 + 一个后台同步线程**。
> 网页本身**几乎只读本地库**,从不直接连微信读书;只有"同步任务"才走 HTTP 去微信读书
> 抓数据并写库。

类比:本地 cache(SQLite)+ 一个 daemon 定期 `sync` 上游(微信读书),前端只查 cache。
因此"拉取"和"存储"集中发生在**一个动作**里(同步任务),其余所有点击都是本地只读。

---

## 一、唯一的"写入时刻":同步任务(拉取 + 存储)

只有三种触发,且最终都汇聚到**同一个后台同步任务**:

| 触发 | 说明 | 相当于 |
|---|---|---|
| 首次启动、库里没数据 | 进程起来自动同步一次 | 进程启动时 sync 一次 |
| 定时器到点(每 N 小时) | 间隔可在 admin 页改 | cron / timer 线程 |
| admin 点「立即刷新」 | `POST /api/refresh` | 手动触发 |

**点「立即刷新」时发生的事:**

1. handler 不阻塞——后台起一个 daemon 线程跑同步,HTTP 立刻返回。页面随后**轮询状态接口**
   等同步结束并弹结果提示,交互细节见 [refresh-interaction.md](refresh-interaction.md)。
2. 进程级 **mutex 的 try-lock(非阻塞)**:三种触发(启动 / 定时 / 手动)共用**同一把锁**,
   若已有同步在跑,这次直接丢弃,保证全局只有一个同步在执行。
3. 后台线程按固定顺序走 HTTP(同一个网关地址,Bearer token,**调用间隔 0.5s**,失败指数
   退避重试),分两个阶段:

   **阶段 A——主同步(整批在一个事务里提交):**
   1. 阅读统计(总 / 月 / 周)
   2. 书架
   3. 笔记本清单(游标分页)
   4. 逐本拉划线 / 想法(只抓 `noteCount` / `reviewCount` > 0 的书)
   5. 推荐(非必需,失败只记一笔、不影响其余)

   这五步**要么一起提交、要么整体回滚**,把"核心数据"(统计 / 书架 / 笔记 / 划线)当成一个
   一致性单元——这才是它们同处一个事务的原因,而**不是**因为它们不走网络(其实 3 / 4 也在
   事务里逐本打 HTTP)。

   **阶段 B——补书籍元数据 `/book/info`(主事务提交之后,每本一个独立短事务):**
   - 覆盖**所有还缺元数据的书**(`info_fetched==0`)。首次同步约等于"整张书架 ∪ 笔记本 ∪
     推荐"的全集;此后靠 `info_fetched` 写一次标记,每天只补新书,
     增量极小。

这一步同时就是"存储",落库方式见第三节。

> **唯一的例外**:admin 页"测试 API key"会同步发一个测试请求验证 key 是否有效,但
> **不存任何东西**。除此之外,网页线程从不直接连微信读书。

## 二、其余所有页面操作:纯本地读

| 页面操作 | 走网络? | 背后做了什么 |
|---|---|---|
| 打开**概览** `/` | 否 | 查本地:最新统计快照 + 每日时长,算连续天数 / 总数,渲染 HTML |
| 概览页的**图表** | 否(只连自己的后端) | 页面 AJAX 调 `/api/stats/trend` → 返回本地库 JSON → Chart.js 绘图 |
| 打开**书架** `/shelf` | 否 | 查最新一份书架快照 + 关联书表,渲染网格 |
| **点一本书** `/book/{id}` | 否 | 查该书划线 / 想法,按章节归并渲染(纯读,**不写库**) |
| 打开**笔记** `/notes` | 否 | 列出有笔记的书,按数量排序 |
| 打开**发现** `/discover` | 否 | 查最新一份推荐快照 |
| **导出 Markdown** `/export/notes/{id}.md` | 否 | 用本地数据拼 markdown 文本 |
| admin **保存设置** | 否(本地写) | 一次很小的本地 DB 写 |

**两个容易误会的点:**

- 书架封面图是**浏览器**直接去微信读书 CDN 拉的(`loading="lazy"`,滚到才加载),与本项目
  的数据库 / 同步**无关**。
- 概览图表的 AJAX 调的是**本项目自己的** `/api/stats/trend`,数据来自本地库,**不是**微信读书。

## 三、存储:两种表,对应两种数据结构

| 写法 | 类比 | 哪些数据 | 重复同步的结果 |
|---|---|---|---|
| **按主键 upsert(就地覆盖)** | hashmap(key → value) | 书、划线、想法、每日时长 | 同一条覆盖原行,**不重复** |
| **按日期追加快照** | 时序 append log(key 带日期) | 书架、推荐、统计 | 每次同步各存一份,**故意保留**以看趋势 |

- **hashmap 类**:主键是 `book_id` / `bookmark_id` / 日期等。今天和明天重合的内容塌缩成
  一行,只保留最新态。upsert 时**只覆盖非空字段**,所以多来源(书架 / 笔记本 / book_info)
  能逐步补全同一本书,不会用空值冲掉已有值。
- **快照类**:主键里带 `pull_date`。书架今天一份、明天一份,即使内容几乎一样——这正是它
  相对微信读书 App 多出的"时间维度"。快照类用"先删当天再插"的方式,保证**同一天重复同步
  是幂等的**,只有跨天才新增一份。

## 四、并发与锁

- **单进程多线程**:web 请求跑在线程池上;同步跑在自己的后台线程;定时器又是一个线程。
- **SQLite 是单写者**:同步的主事务持有写锁期间,**读**(看页面)基本不受影响,但**并发
  写**会阻塞,超时即 `database is locked`。
- 书籍元数据采用**写一次**(`info_fetched` 标记):首次同步补全所有书,之后每天只补"自上次
  同步以来的新书",增量极小。

---

## 一句话总结

**"刷新"是唯一会连微信读书并写库的动作;其它每一次点击都只是在查本地 SQLite。**
拉取 = 那一次后台同步;存储 = 同步时按"hashmap 覆盖 / 时序快照"两种方式落库。
